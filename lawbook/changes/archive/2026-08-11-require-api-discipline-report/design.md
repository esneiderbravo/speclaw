# Design — require an API discipline report

## Approach

Reframe discipline reports as an **open set** — one report per discipline a
change touched, named for that discipline — and call out `api` as mandatory
whenever an API surface is touched. Touch every place the library enumerated the
disciplines so the closed backend/frontend framing does not linger, and ship a
**library rule** so the obligation travels into every speclaw-initialized
project. `ai-specs/` is gitignored (regenerated by init/update), so only the
tracked sources below are edited.

Files in play (markdown / asset docs + the config generator):

1. **New rule** — `src/modules/lawbook/assets/rules/spec-reports-disciplines.md`
   (source of truth, `copyRendered` into `ai-specs/rules/`). It states: reports
   are per-discipline and the set is **open, not fixed** (backend/frontend/api
   are common; database/infra/security/performance/e2e/… are written when the
   change touches them); each touched discipline is mandatory; `api.md` is
   mandatory whenever a change touches an API surface (new/modified endpoint or
   contract), and a backend/frontend report does not substitute for it; and what
   `api.md` must document (contract, status codes, ordering, how it was exercised
   without mutating a live store).
2. **`build` skill Step 5** (`src/modules/lawbook/assets/skills/build/SKILL.md` +
   the self-hosted `ai-specs/skills/build/SKILL.md`) — name `api.md` in the
   discipline list and add the API-surface obligation.
3. **`draft` skill** reports-scaffold guidance (asset + self-hosted) — name
   `api.md` among the disciplines the scaffolded `reports/README.md` lists.
4. **`docs/standards/testing-standards.md`** — name `api.md` in the reports
   section and add the API-surface obligation.
5. **`lawbook/config.yaml`** — reword the mandatory reports step to name
   backend/frontend/api explicitly.
6. **Canonical spec** — promoted from this change's delta at `sync`.

## Why a rule, not an engine gate

The archive gate is deterministic: it can count files under `reports/` but it
cannot know whether a change "touches an API surface" — that is a semantic
judgment over the diff, exactly the kind of thing the agent makes and the engine
deliberately does not (the same reason `lawbook_sync` stays code-blind). So the
`api.md` obligation is enforced the way the backend/frontend obligation already
is: as a rule the coding agent follows, backed by the spec's normative
scenarios. Growing the engine to infer API surfaces was considered and rejected
as both unreliable and a violation of the "engine stays deterministic" law.

## Alternatives weighed

- **Amend the existing `spec-tasks-mandatory-steps` rule instead of adding a new
  one.** Rejected: that rule is about the *ordered task steps*; the discipline
  set and the API-report obligation are a distinct, reusable concern that reads
  better as its own always-applied rule. The existing rule's report bullet is
  still updated to name `api`, so the two stay consistent without overloading
  one file.
- **Make `api.md` a hard archive-gate requirement.** Rejected per the section
  above — non-deterministic; would either over-block (demand `api.md` on a
  docs-only change) or need code inspection the engine forbids.
- **Only document it in the standards, no rule.** Rejected: rules are the
  law-adjacent artifact that ships into `.claude`/`.cursor`/`.codex`/`.agents`
  and is `alwaysApply`, so it is the surface that actually steers agents. A
  standard alone would not travel with the same force.

## Trade-offs

- The obligation depends on the agent correctly recognizing an API surface. This
  matches the existing backend/frontend model and is acceptable; the spec
  scenarios make the expectation testable in review even though the engine does
  not enforce it.
- Touching six files for one conceptual change is deliberate: the library states
  the discipline set in several voices (rule, skills, standard, config, spec),
  and leaving any one un-updated would let the old two-discipline framing linger.
